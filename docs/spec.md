## 1. 概要 / 目的

就活生が複数の求人サイト・メールアカウントに散らばった選考情報を1画面に集約するダッシュボード。
利用者は理系大学院生（ペルソナ：佐々木 拓海・修士1年・エントリー20〜30社）。ゼミ・研究・課題と
就活が衝突し、メールの手動仕分けと情報の転記に時間を奪われている。

ゴールは **「情報整理や連絡対応の手間を最小化し、浮いた時間を研究や課題に充てる」**。
そのため画面の最上部に常に **「研究にあてられる時間」** を出し、就活タスクを減らすと研究時間が
増えることを可視化する。開いたら今日の動きだけが分かる、を最優先にする。

### AI（Azure OpenAI）の利用について

**AI 呼び出しを行う。** 2026-08-03、社内で用意された **Azure OpenAI（Responses API）** に切り替えた
（経緯は `docs/decisions.md` 参照）。Notion「機能選定」の「AI使用の際 学習に使わない設定が必要」という
懸念について、**このAzureリソースが学習に入力を使わない設定になっているかは未確認**。
発表前に確認し、確認できていない場合はその旨を発表資料に明記する。

AI を使う箇所は 2 つだけ。それ以外は AI を使わない。

| 箇所 | 役割 | 失敗時 |
|---|---|---|
| メール分類（③） | ルールで決まらないメールのカテゴリを判定 | ルールベースの既定値 `確認` に落とす |
| 想定問答の生成（④） | 想定質問と回答骨子のリストを生成 | `seed/questions.json` のテンプレ質問を返す |

**ヒーローの1文・プロフィールの推敲・企業マッチングに AI は使わない**（ヒーローの1文は §4 の生成規則どおり
プログラムで組み立てる）。

### AI 呼び出しの規約（ここに書いた形から外れない）

| 項目 | 値 | 理由 |
|---|---|---|
| SDK | `openai`（公式 Python SDK）の`AzureOpenAI`クライアント | `requests` で直叩きしない |
| API 種別 | **Responses API**（`client.responses.parse()`） | 社内Azureリソースのエンドポイントが`/openai/responses`向けのため。Chat Completions API（`client.chat.completions.parse()`）は`response_format`パラメータが使えず400エラーになる |
| モデル / デプロイ名 | `.env`の`AZURE_OPENAI_DEPLOYMENT`（デプロイ名を渡す。モデル名を直接指定しない） | Azureはデプロイ名でモデルを指定する方式のため |
| 出力の受け取り | `text_format=`に Pydantic モデルを渡す（構造化出力） ／ `res.output_parsed`で受け取る | JSON をパースするコードを書かない。型付きで受け取る |
| refusal 判定 | `res.output`内に`type="refusal"`のコンテンツがあるか、または`res.status`が`"failed"`/`"incomplete"` | Chat Completions APIの`message.refusal`とは構造が異なる |
| API キー等 | `.env`の`AZURE_OPENAI_API_KEY`・`AZURE_OPENAI_ENDPOINT`・`OPENAI_API_VERSION`・`AZURE_OPENAI_DEPLOYMENT`（`python-dotenv`で読む） | リポジトリにコミットしない。`.env.example`だけ置く |
| キー未設定時 | 例外を投げず、各機能のフォールバックに落とす | デモが止まらないことを優先 |

呼び出しは `backend/services/ai.py` に集約し、**そこ以外から `openai` を import しない**。

### Google カレンダー呼び出しの規約（ここに書いた形から外れない）

| 項目 | 値 | 理由 |
|---|---|---|
| 認可フロー | `google_auth_oauthlib.flow.Flow`（web サーバー用） | `InstalledAppFlow` は使わない（ローカルブラウザを勝手に開くのでサーバーから使えない） |
| 生成方法 | `Flow.from_client_config(client_config, scopes, redirect_uri=...)` | `client_secret.json` をリポジトリに置かず `.env` の値から組む |
| スコープ | `https://www.googleapis.com/auth/calendar.readonly` のみ | 書き込み権限を取らない（§2 やらないこと） |
| 認可 URL | `flow.authorization_url(access_type="offline", prompt="consent")` | `offline` でないと `refresh_token` が返らない。**`include_granted_scopes` は渡さない**（同じクライアントで別の Google 連携を認可済みだと、Google が付与済みスコープを合わせて返し、oauthlib が `Scope has changed` で認可を失敗させる。実測で確認） |
| PKCE | `Flow` は既定で PKCE 有効（`autogenerate_code_verifier = True`）。`authorization_url()` が生成する `flow.code_verifier` を `OAuthToken.code_verifier` に保存し、`callback` で**同じ値を新しい `Flow` に注入してから** `fetch_token` する | 無効化しない。保存せず `Flow` を作り直すと Google が `invalid_grant: Missing code verifier.` を返す（実測で確認） |
| トークン取得 | `flow.fetch_token(code=...)` → `flow.credentials` | 手で HTTP を叩かない |
| 資格情報の再構築 | `google.oauth2.credentials.Credentials(token=..., refresh_token=..., token_uri=..., client_id=..., client_secret=..., scopes=[...])` | DB の `OAuthToken` から毎回組み直す |
| 失効時 | `credentials.expired` が真なら `credentials.refresh(google.auth.transport.requests.Request())` → 新しい値を `OAuthToken` に保存 | アクセストークンは約1時間で切れる |
| API 呼び出し | `googleapiclient.discovery.build("calendar", "v3", credentials=creds)` → `service.events().list(...)` | REST を直叩きしない |
| 認可情報 | `.env` の `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `GOOGLE_REDIRECT_URI` | コミットしない。`.env.example` にキー名だけ置く |
| リダイレクト先 | `.env` の `FRONTEND_ORIGIN`（既定 `http://localhost:5173`）を前に付けた**絶対 URL** | 相対パスだとブラウザが API 側（8000番）を開いて 404 になる（実測で確認）。画面は Vite 側にある |
| 未設定・未認可時 | 例外を投げず、`seed/calendar.json` の従来同期に落とす | デモが止まらないことを優先（AI と同じ方針） |

Google API の呼び出しは用途ごとに1モジュールへ集約する（`services/ai.py` と同じ方針）。
カレンダーは `backend/services/gcal.py`、Gmail は `backend/services/gmail.py`。
**この2つ以外から `google_auth_oauthlib` / `googleapiclient` / `google.oauth2` を import しない。**

**フォールバック先は連携ごとに違う。**「例外を投げずデモを止めない」方針は共通だが、
落とし先は次のように書き分ける。

| 連携 | 未設定・未認可・取得失敗のときの挙動 |
|---|---|
| カレンダー | `seed/calendar.json` を読み直して upsert する（`source = "seed"`） |
| Gmail | **何も書き換えず件数0を返す**（`source = "seed"`）。受信箱は既に入っている seed のメールを表示し続ける |

Gmail が seed を読み直さないのは、`seed/emails.json` に `external_id` が無く、
再投入すると同じメールが重複して増えるため（カレンダーは `external_id` を持つので upsert できる）。

認可時のスコープ検査の緩和だけは2つに共通するので `backend/services/oauth_scope.py` に置く。
同じクライアント ID で2つの連携を持つと、片方を認可済みの状態でもう片方を認可したときに
Google が付与済みスコープを合わせて返し、oauthlib が `Warning: Scope has changed ...` を投げて
認可を失敗させるため（実測で確認）。緩めるスイッチがプロセス共有の環境変数なので、
ロックごとここに集約する。

### スタイルについて（Notion 技術選定からの明示的な変更）

Notion 技術選定は Tailwind CSS だが、**採用しない**。案03の完成形 `03-today-focus/index.html` が

### テストランナーについて（CLAUDE.md からの明示的な逸脱）

CLAUDE.md は「テストランナーは1つに絞る」としているが、**各層1つずつ**とする。
理由：検証したいロジックが2層に分かれている（メール分類・空き時間算出＝Python／
充実度計算・タイムライン差し込み表示＝TypeScript）。1つに絞るとどちらかがテスト不能になる。

| 対象 | ランナー | 置き場所 |
|---|---|---|
| 分類・集約・空き時間などの純ロジック | pytest | `backend/tests/` |
| 表示ロジック・コンポーネント | Vitest | `frontend/src/**/*.test.ts(x)` |

### AI 部分のテスト方針（LLM の非決定性への対処）

CLAUDE.md は「緑にするために期待値を実挙動へ書き換えない」と定めている。一方 LLM の出力は
実行ごとに変わるため、**AI の出力内容そのものをテストの期待値にしない**。テストするのは
「AI の周りのコードが正しいか」だけに絞る。

| テストする | テストしない |
|---|---|
| Claude が返した構造化出力を正しく DB に保存できるか | Claude がどんな質問文を生成するか |
| API キー未設定のときフォールバックに落ちるか | 分類結果が人間の感覚と一致するか |
| 通信失敗・`refusal` のときフォールバックに落ちるか | 回答骨子の文章の質 |
| ルールで決まるメールを AI に投げていないか（呼び出し回数） | — |

**実装方法**：`services/ai.py` の Azure OpenAI 呼び出しをテスト時にモックへ差し替える
（`unittest.mock.patch` で `services.ai._get_client` を置き換える）。**pytest では実 API を叩かない**
ため、`AZURE_OPENAI_API_KEY`等はテスト実行に不要。

実 API での動作確認は**手動**で行い、結果は仕様書に書き戻さない（§付録のデモ動線でまとめて確認する）。

### 起動・確認

```bash
# バックエンド
cd backend
pip install fastapi uvicorn sqlmodel python-dotenv pytest httpx openai
pip install google-auth google-auth-oauthlib google-api-python-client   # §5.7 の Google 連携用
cp ../.env.example ../.env           # AZURE_OPENAI_API_KEY 等 / GOOGLE_* を書く（未設定でも起動する）
python -m seed.load                  # seed JSON を SQLite に投入（毎回作り直し）
```

### 4.1 今日（ホーム）`/`

- **目的**：開いたら今日の動きだけが分かる。何をすればいいかが一目で決まる。
- **ヒーロー**
  - 日付（`2026年7月30日（木）`）／1文（`今日やることは 5件。まず ES 提出から。`）
  - 指標4つ：`研究にあてられる時間` `空き時間` `就活タスク` `要対応メール`
    （スマホ幅で残る先頭2つを時間の指標にする。`予定` の件数は右のタイムラインで分かるので出さない）
  - 1文の生成規則：未完了タスクが0件なら `今日の就活タスクはありません。研究に集中できます。`、
    1件以上なら `今日やることは {未完了件数}件。まず {締切が最も近い未完了タスクの短縮名} から。`
- **左カラム（`.col` で縦2枚）**
  - 上：`✓ 今日やること` — 各行にチェックボックス（`.chk`）・タイトル・補足（締切）・タグ
  - 下：`✉ 今日返すべきメール` — `needs_reply = true` のメール。カテゴリタグ＋件名＋企業名・時刻
  - どちらも**件数で切らず、カード内（`.body.scroll`）のスクロールで全件たどれるようにする**。
    ページ自体は `100dvh` ＋ `overflow:hidden` のままなのでブラウザのスクロールバーは出ない
    （2026-08-03 改訂。`＋ 他 N件` は使わない）
- **右カラム**
  - `▣ 今日のタイムライン` — 時間スロットの縦並び。就活イベント＝ティール、学業＝グレー（`.ev.cls`）、
    研究枠の空き＝`.ev.study`（ティールの破線枠）に **「研究 Nh」**、
    研究枠の外の空き＝斜線背景（`.ev.free`）に **「空き Nh ― {タスク名} をここに」** を差し込む。
    末尾に翌日の先頭イベント1件。これもカード内スクロールで全件見せる
- **操作と結果**
  - タスクのチェックボックスをクリック → `is_done` を反転（`PATCH /api/tasks/{id}`）。
    完了行は `.done`（打ち消し線＋グレー）になり、ヒーローの `就活タスク` と `空き時間` が再計算される。
    `研究にあてられる時間` は予定だけで決まるので動かない
  - **完了しても行を末尾へ動かさない。**締切順のまま打ち消し線で表す（どれを片付けたかが分かるようにするため）
  - **締切を過ぎているのに未完了の行は黄色文字**（`--warn`）にする（`.task.over`）。
    判定は §5.3 の基準時刻と比較する
  - 各カードの `すべてのタスク →` / `受信箱 →` / `カレンダー →` で該当画面へ
  - タスク行・メール行のクリックは**今回は遷移しない**（詳細画面は対象外）

### 4.2 カレンダー `/calendar`

- **目的**：就活と学業の衝突を見つけ、空いている時間を把握する。
- **ヒーロー**：1文は `{今日の日付} は{衝突があれば「面接とゼミが重なっています。」／なければ「衝突はありません。」}`
- **表示要素**
  - FullCalendar の **月表示（dayGrid）／週表示（timeGrid）** をトグル。初期表示は週
  - イベントは種別で色分け：`選考` = ティール、`学業` = グレー。
    **画面に出す表示ラベルは `就活` / `学業`**（凡例・ヒーロー指標・詳細モーダル）。
    DB・API の `Event.kind` の値は `選考` のまま変えない（表示だけを言い換える）
  - イベントの予定名は枠から溢れさせない。週表示は**時刻と予定名を縦2段にし、予定名は2行で省略**、
    月表示は1行で省略する。全文は次項の詳細モーダルで確認する
  - 右または下に `同期` ボタン（このページの主要アクション。1つだけ）
  - **連携状態の表示**（§5.7）：`GET /api/calendar/status` の `connected` に応じて、`同期` ボタンの横に
    小バッジを出す。`true` → `Google 連携中`（ティール系 `.tag`）／`false` → `Google 未連携`（グレー版 `.tag`）。
    未連携のとき**バッジ自体がリンク**になり `GET /api/calendar/auth` の `auth_url` へ遷移する。
    **主要アクションは `同期` のまま1つ**（バッジはボタンにしない。案03のルールを崩さないため）
  - **候補日カード**（§5.7.3）：右カラムに `◇ 面接の候補日` — `GET /api/calendar/suggest` の3件を
    `8/5（水）14:00〜15:00` の形で並べる。0件なら `7日以内に {duration}分 空いている枠がありません`
- **操作と結果**
  - `同期` → `POST /api/calendar/sync`。Google 認可済みなら実カレンダー、未認可なら `seed/calendar.json`
    から `external_id` で upsert（**同じボタンを2回押しても件数が増えない**）。完了後カレンダーを再取得。
    結果のトーストに `source` を出す（`Google から 12件`／`seed から 6件`）ので、
    **どちらから取り込んだかが画面で分かる**
  - `Google 未連携` バッジ → Google の認可画面へ。許可後 `/calendar?connected=1` に戻り、
    バッジが `Google 連携中` に変わってトーストで `Google カレンダーと連携しました` を出す
  - 候補日カードの行クリックは**今回は遷移しない**（日程調整メールの送信は対象外）
  - イベントのクリック（スマホはタップ）→ **読み取り専用の詳細モーダル**を開く。
    出す項目は 予定名・種別（`就活` / `学業`）・日時（`7/30（木）15:00〜16:00` の形）・場所の4つだけ。
    `閉じる` ボタンまたは Esc で閉じる。**主要アクションは `同期` のまま1つ**（モーダルはボタンを増やさない）
  - 日付クリックは今回対象外。イベントクリックでも**編集はしない**（表示専用）

### 4.3 受信箱 `/inbox`

- **目的**：gmail と iCloud のメールを1つの箱で見て、返すべきものを先に見つける。

- **表示要素**
  - カテゴリのフィルタチップ：`すべて / 重要 / 確認 / 広告`（初期は `すべて`）
  - メール一覧：**企業 × スレッドで1グループに畳む**。グループ行に企業名・件名（正規化後）・

  - カテゴリの色：重要 = `.tag.d`（赤系）／確認 = `.tag.w`（黄系）／広告 = `.tag`（ティール系）

### 4.4 プロフィール `/profile`

- **目的**：ES やマイページに何度も書く内容を1か所に置き、コピーで使い回す。
- **ヒーロー**：1文は 未入力があれば `未入力は「{未入力項目名の列挙}」だけ。埋めれば想定問答が作れます。`、

  指標に `充実度` を含める
- **表示要素**：9項目のカードを **3列 × 3行**で並べる。行ごとに意味をそろえる

  - 指標4つ：`研究にあてられる時間` `準備率` `想定質問` `未準備`

- **表示要素**
  - ヒーロー直下に企業セレクト（`seed/companies.json` の4社から選ぶ）＋ `想定問答を生成`
    ボタン（このページの主要アクション。1つだけ）

## 5. 処理フロー

### 5.1 メール分類（`services/classifier.py` ＋ `services/ai.py`）

**ルール優先 ＋ AI フォールバック。** ルールで決まるものは AI に投げない。

#### 5.1.1 ルール判定（`services/classifier.py`。純関数・AI を呼ばない）

**設計方針（2026-07-31 改訂）**：分類は**送信元ドメインではなく件名の内容**で決める。
以前あった「ドメインを登録すると一律そのカテゴリになる」`DomainRule` の仕組みは廃止した。
同じ企業からのメールでも、件名の内容次第で `重要` にも `広告` にもなる。

**入力**：`Email` の `subject`
**処理**：以下を**上から順に評価し、最初に一致したものを採用する**（同じ入力なら常に同じ結果）

| 優先 | 条件 | 結果 | `decided_by` |
|---|---|---|---|
| 1 | `subject` が `面接｜日程｜選考結果｜内定｜お祈り｜最終` に一致 | `重要` | `rule` |
| 2 | `subject` が `配信停止｜メルマガ｜セミナー案内｜PR｜スカウト｜おすすめ求人` に一致 | `広告` | `rule` |
| 3 | `subject` が `ES｜エントリーシート｜提出｜期限｜リマインド｜説明会` に一致 | `確認` | `rule` |
| 4 | 上のいずれにも一致しない | **判定を保留**（`None` を返す） | — |

正規表現は大文字小文字を区別しない。判定は**件名のみ**を見る（送信元・本文は見ない。
`from_address` はグルーピング／スレッド化にのみ使う）。
**エラー時**：件名の文字列一致のみで判定するため、不正な入力による例外は発生しない。

#### 5.1.2 AI フォールバック（`services/ai.py`）

**入力**：5.1.1 が保留した `Email` の `subject` と `from_address`（**本文は渡さない**）
**処理**：Azure OpenAI（Responses API）に構造化出力で分類させる。

```python
class EmailCategory(BaseModel):
    category: Literal["重要", "確認", "広告"]
    needs_reply: bool
    reason: str  # 1文。UI には出さないがログとデモの説明に使う

res = client.responses.parse(
    model=os.getenv("AZURE_OPENAI_DEPLOYMENT"),
    instructions=(
        "あなたは就活生のメールを3カテゴリに分類する。"
        "重要=面接や選考結果など今日中に見る必要があるもの。"
        "確認=ESや説明会など期限があるが即応でないもの。"
        "広告=スカウトやメルマガなど読まなくても支障がないもの。"
    ),
    input=f"送信元: {email.from_address}\n件名: {email.subject}",
    text_format=EmailCategory,
)
result = res.output_parsed  # EmailCategory インスタンス
```

- 保留メールは**1通ずつ**呼ぶ（バッチにしない。1通失敗しても他が巻き添えにならないため）
- 結果を採用したものは `decided_by = "ai"`
- **本文を渡さない**のは、個人情報を API に送る量を最小にするため。発表でもそう言える

**出力**：`Email.category` / `Email.needs_reply` / `Email.decided_by`。
`decided_by = "rule"` の場合の `needs_reply` は「`重要` かつ 件名が `日程｜要返信｜ご連絡` に一致」で決める。

**エラー時（すべて例外を投げず、デモを止めない）**

| 状況 | 挙動 |
|---|---|
| Azure OpenAIの認証情報未設定 | AI を呼ばず `category = "確認"` / `decided_by = "rule"` |
| API 通信失敗・タイムアウト・レート制限 | 1回だけ再試行し、それでも失敗なら `category = "確認"` / `decided_by = "rule"` |
| `res.output`に`type="refusal"`のコンテンツがある、または`res.status`が`"failed"`/`"incomplete"` | `content` を読まず `category = "確認"` / `decided_by = "rule"` |
| 返ってきた `category` が3値以外 | 構造化出力が保証するので起こらないが、念のため `確認` に落とす |

いずれのフォールバックでもサーバーログに1行残す（発表で「落ちてもこう動く」と示せるように）。

### 5.2 企業・スレッドの集約（`services/grouping.py`）

### 5.3 研究にあてられる時間・空き時間・空きスロット（`services/freetime.py`）

> 2026-08-03 改訂。**研究は大学院に居る間しかできない**ため、可処分時間を「研究枠」と
> 「それ以外」に分けた。ペルソナのゴール（連絡対応の手間を減らし、浮いた時間を研究や課題に充てる）を
> 2つの指標で見せるための変更。

**入力**：対象日、その日の `Event` 一覧、その日締切の未完了 `Task` 一覧

可処分時間 = **08:00〜22:00 の 14 時間**（固定）。その内訳を次の2枠に分ける。

| 枠 | 範囲 | 意味 |
|---|---|---|
| 研究枠 | **10:00〜17:00（7h）** | ここの空き ＝ `研究にあてられる時間` |
| 研究枠の外 | 08:00〜10:00 ／ 17:00〜22:00（計 7h） | ここの空き ＝ `空き時間`（就活にあてる） |

**処理**

1. `研究にあてられる時間 = 7h − 研究枠に重なるイベントの占有時間`
   - **タスクの見積りは引かない。**研究できる時間帯は予定だけで決まる
2. `空き時間 = 14h − 研究枠 7h − 研究枠の外のイベントの占有時間 − 未完了タスクの見積り合計（estimate_min）`
   - タスクを引くのは「手間を減らすと浮く時間が増える」を数字で見せるため。
     チェックを付けるとその見積り分だけ空き時間が増える
3. 1・2 とも、重なり合うイベントは重複を除いた実占有時間で数える。
   結果が負なら `0h`。表示は 0.5h 刻みに丸める（小数第1位まで）。
   丸めは**半数切り上げ**（Python の `round()` は偶数丸めなので使わない。
   7.25h→7.0h・7.75h→8.0h と挙動が揺れて説明できなくなるため）
4. 空きスロット = **研究枠の外**からイベント時間を差し引いた連続区間のうち **30分以上**のもの。
   研究枠の中には空きスロットを作らない（研究の時間を就活で潰さないため）
5. 各空きスロットに、**締切が最も近い未完了タスクを1つだけ**差し込む（既に差し込んだタスクは再利用しない）
6. 研究枠の空き（30分以上）は `research_slots` として返し、タイムラインに `研究 Nh` と表示する

**出力**：`{research_hours, free_hours, free_slots: [{start, end, suggested_task}], research_slots: [{start, end}]}`
**エラー時**：イベントが0件なら空きスロットは 08:00〜10:00 と 17:00〜22:00 の2件、
`research_slots` は 10:00〜17:00 の1件。タスクが0件なら `suggested_task = null` とし、
表示は `空き Nh` のみにする。

**基準時刻**：2026-08-05 にチームで合意の上、`resolve_day()` / `resolve_now()`（`services/freetime.py`）の
既定値を固定日時から**実際の `date.today()` / `datetime.now()`**に切り替えた。`SEED_NOW_TIME`（`12:20`）は
当日以外の日付（タスクの締切日など）と組み合わせるときの代用値としてのみ残す。フロントの
`Calendar.tsx`の`BASE_DATE`も同様に実日付へ切り替え済み。`seed/*.json`のダミーデータ自体は
引き続き2026-07-30前後の日付のままなので、実際の「今日」がその範囲から離れるほど、
カレンダー・タスクの表示は空に近づく（デモ時はこの点に注意する）。

**入力**：`POST /api/calendar/sync`
**処理**：`seed/calendar.json` を読み、`external_id` をキーに **upsert**（既存は更新、無ければ追加）
**出力**：`{added: n, updated: m}`。フロントは件数をトーストで表示し、イベントを再取得

### 5.5 プロフィール保存

**入力**：`PUT /api/profile` に9項目
**処理**：単一レコード（`id = 1`）を更新。レコードが無ければ作成。空文字は許容する
**出力**：更新後のプロフィール ＋ `completeness`（= 空でない項目数 ÷ 9 を四捨五入した整数%）
**エラー時**：各項目 8000 文字超なら 422 と項目名を返し、保存しない（1項目でも超過したら9項目とも保存しない）

補足（実装時に決めた解釈。ここを正とする）

- **「空でない」の判定は前後の空白を除いた結果で行う。**空白のみの入力は未入力として数える
  （画面上は空に見えるのに充実度だけ上がるのを防ぐため）
- `GET /api/profile` はレコードが未作成でも 404 にせず、9項目すべて空文字・`completeness = 0` を返す。
  GET では DB に書き込まない（作成は PUT のときだけ）
- 8000 文字は Python の `len()`（Unicode コードポイント数）で数える

### 5.6 想定問答の生成（`services/ai.py`）

**入力**：`POST /api/qa/generate` に `company_id`。サーバー側で `Profile`（全9項目）と
`Company`（`name` / `tags`）を読む
**処理**

1. `Profile` が**全項目空**なら AI を呼ばず 422 と `プロフィールを1項目以上入力してください` を返す
2. Azure OpenAI（Responses API）に構造化出力で生成させる（Notion 技術選定 F の形をそのまま使う）

```python
class QA(BaseModel):
    question: str
    answer_draft: str
    category: Literal["志望動機", "ガクチカ", "逆質問"]

class QASheet(BaseModel):
    items: list[QA]

res = client.responses.parse(
    model=os.getenv("AZURE_OPENAI_DEPLOYMENT"),
    instructions=(
        "あなたは就活生の面接対策を手伝う。渡されたプロフィールと企業情報から、"
        "その企業の面接で実際に聞かれそうな想定質問と、回答の骨子を作る。"
        "回答骨子はプロフィールに書かれた事実だけを使い、経歴を創作しない。"
        "質問は6〜8問、各カテゴリを少なくとも1問含める。"
    ),
    input=prompt,  # プロフィール9項目＋企業名＋タグ
    text_format=QASheet,
)
sheet = res.output_parsed
```

3. 生成結果を `QA` テーブルに保存する。**同じ `company_id` の既存レコードは全削除してから入れ替える**
   （再生成で件数が増えていかないように）。`is_prepared` は `false` で入る
4. `source` に `ai` を入れる

**出力**：`{company_id, source, items: [...], prepared_rate}`。
`prepared_rate` = `is_prepared` が true の件数 ÷ 総件数（整数%。0件なら 0）

**エラー時（フォールバック）**

| 状況 | 挙動 |
|---|---|
| Azure OpenAIの認証情報未設定 | `seed/questions.json` のテンプレ質問セットを保存し `source = "template"` で返す |
| API 通信失敗・タイムアウト・レート制限 | 1回だけ再試行し、それでも失敗ならテンプレにフォールバック（`source = "template"`） |
| `res.output`に`type="refusal"`のコンテンツがある、または`res.status`が`"failed"`/`"incomplete"` | `content` を読まずテンプレにフォールバック |
| プロフィールが全項目空 | 422。AI もテンプレも呼ばない（1 で弾く） |

**回答骨子の内容に AI が事実を創作していないかは自動で検証しない**（システムプロンプトで抑止するに留める）。
発表前に人間が1度目視する運用にする。

### 5.7 Google カレンダー実連携・候補日おすすめ（`services/gcal.py`）

§5.4 のモック同期を**置き換えず、分岐で足す**。未認可でも従来どおり動くことを最優先にする。

#### 5.7.1 認可（OAuth2 web サーバーフロー）

| メソッド | パス | 処理 |
|---|---|---|
| GET | `/api/calendar/auth` | `flow.authorization_url(...)` で認可 URL を作り、`state` を DB に保存して `{auth_url}` を返す。`.env` の `GOOGLE_*` が未設定なら 503 と `Google 連携が設定されていません` を返す（例外にしない） |
| GET | `/api/calendar/callback` | クエリ `code` / `state` を受け取る。`state` が保存値と一致しなければ 400。一致すれば `flow.fetch_token(code=...)` → `flow.credentials` を `OAuthToken`（`provider = "google"`）に upsert し、`/calendar?connected=1` へ 302 リダイレクト |
| GET | `/api/calendar/status` | `{connected: bool, scope: str \| null, expires_at: datetime \| null}`。画面が認可済みかを判定するのに使う |
| DELETE | `/api/calendar/auth` | `OAuthToken` の `google` 行を削除して連携解除。**`Event` は消さない**（他人の同期データを消さない。CLAUDE.md §0-⑥） |

- `state` は CSRF 対策。`OAuthToken.auth_state` に一時保存し、`callback` で照合したら消す
- **`code` / `access_token` / `refresh_token` をログ・レスポンス・エラーメッセージに出さない**

#### 5.7.2 同期（`POST /api/calendar/sync` の分岐）

```
OAuthToken に google 行があるか？
├─ ある  → Google Calendar API から取得して upsert（source = "google"）
│           取得失敗（RefreshError / HttpError / タイムアウト）なら1回だけ再試行し、
│           それでも失敗なら seed 同期に落として source = "seed" で返す
└─ ない  → 従来どおり seed/calendar.json を upsert（source = "seed"）
```

Google から取る範囲は **今日の 00:00 から 14 日後の 23:59**（`timeMin` / `timeMax`）。
`service.events().list(calendarId="primary", timeMin=…, timeMax=…, singleEvents=True,
orderBy="startTime", maxResults=250)` を使い、`nextPageToken` がある限り繰り返す。

Google のイベント → `Event` への写し方

| `Event` の項目 | Google の値 | 補足 |
|---|---|---|
| `external_id` | `f"google:{item['id']}"` | seed の `external_id` と衝突しないよう接頭辞を付ける。これが upsert キーなので**2回同期しても増えない** |
| `title` | `item.get("summary")` | 空なら `（無題）` |
| `start_at` / `end_at` | `item["start"]["dateTime"]` / `item["end"]["dateTime"]` | 終日予定（`date` しか無い）は**取り込まない**（時間占有が計算できず空き時間算出を壊すため） |
| `location` | `item.get("location")` | — |
| `kind` | 既定は `選考`。`summary` が §5.1.1 と同じ大文字小文字無視の正規表現 `ゼミ｜研究室｜講義｜授業｜レポート｜課題｜実験` に一致すれば `学業` | 表示色の出し分けに使う（§4.2）。判定は件名相当の文字列のみで行う |
| `company_id` | `null` | 実カレンダーのタイトルから企業を推測しない（§5.2 と同じ方針） |

- `item.get("status") == "cancelled"` の予定は**取り込まず、既存があれば削除する**（Google 側で消えた予定を残さない）
- **2026-08-05 追加**：`events().list()`（timeMin/timeMax の範囲取得）は削除済みの予定を
  そもそも返さない（`status="cancelled"` が返るのは `syncToken` を使った差分同期のときだけで、
  今回の実装では発生しない）。そのため取得できた範囲に絞って、DB 側にある `google:` 由来の
  既存イベントと今回の取得結果を突き合わせ、**結果に含まれなくなったものも削除する**
  （`services/gcal.py` の `_vanished_external_ids`）
- 出力は `{added, updated, deleted, source}`。`source` は `google` / `seed`

#### 5.7.3 候補日おすすめ

**入力**：`GET /api/calendar/suggest?duration=60`（`duration` は分。既定 60、範囲 15〜480。範囲外は 422）
**処理**
1. 今日から 7 日間の各日について、`services/freetime.py` の空きスロット算出（§5.3）を呼ぶ
2. `duration` 以上の長さを持つスロットだけを残す
3. **同じ日から2件以上は採らない**（候補が1日に固まらないようにする）
4. 開始が早い順に並べ、**上位3件**を返す

**出力**：`{duration_min, slots: [{start, end, label}]}`。`label` は `8/5（水）14:00〜15:00` の形。
**エラー時**：条件を満たすスロットが0件なら `slots: []` を返す（404 にしない）。
画面は空配列のとき `7日以内に {duration}分 空いている枠がありません` と出す（§4.2）。

**§5.3 との関係**：空きスロット算出は `services/freetime.py` の関数をそのまま使い、
**候補日側でロジックを複製しない**。`freetime.py` は今日画面（§4.1）と共有する。

### 5.9 企業マッチング（`services/matching.py`）

> 2026-08-05 追加。`/companies`（企業の発見・マッチング）で使う。
> **AI は使わない**（§2「AI を使うのは2箇所だけ」）。同じ入力なら常に同じマッチ率になる純関数にする。

**入力**：マッチング条件（画面のテンプレ質問の回答）と `Company` 一覧、`Profile.job_axis`

| 条件 | 由来 | 省略時 |
|---|---|---|
| `job_type` | 質問「希望する職種は？」 | 条件に数えない |
| `location` | 質問「希望する勤務地は？」 | 条件に数えない |
| `remote_only` | 質問「リモート勤務は必須？」 | 条件に数えない |
| `salary_min` | 質問「希望年収は？（万円以上）」 | 条件に数えない |
| `holidays_min` | 質問「年間休日は何日以上ほしい？」 | 条件に数えない |
| `axes` | プロフィールの `job_axis`（カンマ区切り）。画面で上書きもできる | 条件に数えない |

**処理**：条件ごとに重みを持たせ、**満たした重みの合計 ÷ 指定された条件の重みの合計** を百分率にする。

| 条件 | 重み | 合致の判定 |
|---|---|---|
| 職種 | 3 | `Company.job_type` が条件を含む（前後の空白を除いた部分一致・大文字小文字を区別しない） |
| 勤務地 | 2 | `Company.location` が条件を含む（同上） |
| 年収 | 2 | `Company.salary_min >= salary_min`。企業側が未登録（`null`）なら**合致しない** |
| 休日 | 1 | `Company.holidays_per_year >= holidays_min`。未登録なら**合致しない** |
| リモート | 1 | `remote_only = true` のとき `Company.remote_ok = true` |
| 就活軸 | 軸1つにつき 1 | `Company.tags`（カンマ区切り）に同じ軸がある（完全一致・前後の空白を除く） |

年収を勤務地と同格の重み 2 にするのは、就活生が実際に強く見る条件だから。
**年収・休日は AI に生成させない**（数値は最も捏造されやすい）。`Company` に保存した値だけを使い、
画面にも同じ値を並記して照合できるようにする。

- **指定された条件が0個なら 0% を返す**（分母が0になるため。「条件を入力してください」と画面に出す）
- 百分率は**四捨五入した整数**。`round()` の偶数丸めは使わない（§5.3 と同じ理由）
- 会社側の項目が空文字なら、その条件は**合致しない**（推測で埋めない。`CLAUDE.md` §E）

**マッチ理由**：合致した条件だけを文言にして返す（例 `職種が一致：ソフトウェアエンジニア`、
`就活軸「成長環境」に一致`）。**合致しなかった条件は理由に出さない。推測で理由を作らない。**

**出力**：`{rate, reasons: [str], matched_axes: [str]}`
**エラー時**：企業が0件なら空リストを返す（エラーにしない）

### 5.10 企業一覧の取得元（`services/company_source.py`）

企業一覧を返す関数をここに集約する。**今回は `Company` テーブル（seed 由来）を返すだけ。**

### 5.11 受信箱からの企業登録の提案（`services/company_source.py`）

> 2026-08-05 追加。**企業を探す手間・登録する手間を減らすための機能。**
> ペルソナの悩み（§1「メールの手動仕分けと**情報の転記**に時間を奪われている」）に直接効く。
> **AI もスクレイピングも使わない。**既に受信しているメールだけを使う。

**入力**：`Email` 一覧、`Company` 一覧

**処理**

1. `company_id` が `null` のメール（＝企業が未登録のドメインから届いたもの）を集める
2. **`category` が `重要` または `確認` のものだけを候補にする。**`広告` は除く
   - エージェント・メルマガ配信元を企業として登録すると選考ボードが埋まって使えなくなるため
   - 判定は既存のメール分類（§5.1）の結果をそのまま使う。新しい判定を作らない
3. 送信元ドメインでまとめ、**企業名の候補は `from_name`（送信者表示名）の最頻値**を使う
   - `from_name` が無ければドメインをそのまま企業名の候補にする
   - **ドメインから企業名を推測しない**（`CLAUDE.md` §E）。あくまで「候補」として画面に出し、人が直せる形にする

**出力**：`[{domain, suggested_name, email_count, latest_received_at, categories}]`。受信の新しい順
**エラー時**：候補が0件なら空配列（エラーにしない）

**登録**：`POST /api/companies/from-emails` にドメインの配列を渡すと、その企業を `stage = 気になる` で作る。
作成後、**そのドメインの既存メールの `company_id` を埋め直す**（受信箱の表示が企業名に変わる）。
既に登録済みのドメインは黙って読み飛ばす（二重登録しない）。

### 5.12 Gmail 実連携（`services/gmail.py`）

> 2026-08-06 追加（§2 やること ⑥）。§5.7 の Google カレンダー実連携と同じ作法で、
> **モックを置き換えず分岐で足す。**未認可でも受信箱が従来どおり動くことを最優先にする。

Gmail API を呼ぶのは `backend/services/gmail.py` だけ（§3 の規約）。

#### 5.12.1 認可（OAuth2 web サーバーフロー）

| メソッド | パス | 処理 |
|---|---|---|
| GET | `/api/gmail/auth` | 認可 URL を作り `state` と `code_verifier` を保存して `{auth_url}` を返す。未設定なら 503 |
| GET | `/api/gmail/callback` | `state` が保存値と一致しなければ 400。一致すればトークンを `OAuthToken`（`provider = "gmail"`）に upsert し、受信箱へ 302 リダイレクト |
| GET | `/api/gmail/status` | `{connected, configured, scope, expires_at}`。**トークン本体は返さない** |
| DELETE | `/api/gmail/auth` | `OAuthToken` の `gmail` 行を削除。**`Email` は消さない**（CLAUDE.md §0-⑥） |

- **スコープは `https://www.googleapis.com/auth/gmail.metadata` のみ。**本文を取得する権限を取らない
- `provider` がカレンダーの `google` と別なので、**片方だけ解除できる**（互いに影響しない）
- `state`（CSRF）と `code_verifier`（PKCE）の扱い、`refresh_token` を空で上書きしないことは §5.7.1 と同じ
- リダイレクト先は `.env` の `FRONTEND_ORIGIN` を前に付けた絶対 URL（§3）

#### 5.12.2 同期（`POST /api/gmail/sync`）

```
OAuthToken に gmail 行があるか？
├─ ある  → Gmail API から取得して upsert（source = "gmail"）
│           取得失敗なら1回だけ再試行し、それでも失敗なら source = "seed" で返す
└─ ない  → Gmail を一切呼ばず source = "seed" で返す（何も書き換えない）
```

| 項目 | 値 | 理由 |
|---|---|---|
| 取得対象 | 受信トレイのみ（`labelIds=["INBOX"]`） | 送信済み・下書きを取り込まない |
| 取得期間 | 直近 **14 日** | カレンダーの `SYNC_DAYS` と幅をそろえる |
| 1回の上限 | **100 件** | 保留メールは1通ずつ AI に投げる（§5.1.2）ので、上限が無いと呼び出しが受信数に比例する。打ち切ったらログに1行残す |
| 絞り込みの順序 | **100件取ってから期間で捨てる** | `gmail.metadata` スコープでは `messages.list` の `q` が使えない（Google が 403 を返す） |
| 取得ヘッダ | `Subject` / `From` / `Date` のみ（`format="metadata"`） | 本文を取らない。`full` はスコープ上そもそも使えない |
| 受信日時 | `internalDate`（エポックミリ秒）を優先し、無ければ `Date` ヘッダ。JST の naive に変換 | `Date` は送信側の時計・書式に依存する |
| ヘッダの復号 | RFC 2047（`=?UTF-8?B?...?=`）を復号する。失敗しても例外を投げず生の値を使う | 日本語の件名・表示名は符号化されて届く。1通の異常で同期全体を落とさない |

`Email` への写し方

| `Email` の項目 | Gmail の値 |
|---|---|
| `external_id` | `f"gmail:{message_id}"`。**これが upsert キーなので2回同期しても増えない** |
| `account` | 固定で `gmail` |
| `from_address` / `from_name` | `From` ヘッダを `email.utils.parseaddr` で分解。読めなければ**その1通を取り込まない** |
| `subject` | `Subject` ヘッダ（復号後）。空文字可 |
| `body` | **常に `null`**（取得しない） |
| `category` / `needs_reply` / `decided_by` | §5.1 の `services/classifier.py` をそのまま呼ぶ。**分類ロジックを複製しない** |
| `company_id` / `thread_key` | §5.2 の `services/grouping.py` をそのまま呼ぶ |

**処理の順序（守る）**：①企業を読む → ②全通の分類を済ませる（DB を触らない）→ ③まとめて書いて1回 commit。
分類は1通ずつ AI を呼ぶので遅く、書き込みを挟みながら回すと書き込みトランザクションを
その間ずっと保持してしまい、画面の定期取得と衝突して `database is locked` になる（実測で確認）。

**出力**：`{added, updated, ai_decided, source}`。`source` は `gmail` / `seed`
**エラー時**：未設定・未認可・取得失敗・`OperationalError` のいずれも例外を投げず `source = "seed"` を返す

## 7. 受け入れ条件
