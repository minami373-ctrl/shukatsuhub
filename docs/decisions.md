## 2026-07-31 骨組みが2箇所に並行して作られた（要注意の事例）

### 何が起きたか

同じ日に2人が別々に開発の骨組みを作り、**同じものが2箇所にできた**。

| | 片方（先に main へ入った） | もう片方（手元で作業） |
|---|---|---|
| 配置 | `job-dashboard/backend` `job-dashboard/frontend` | リポジトリ直下 `backend/` `frontend/` |
| 重複したファイル | `models.py` `db.py` `main.py` `conftest.py` `seed/load.py` `Shell.tsx` `Hero.tsx` `FeaturePanel.tsx` `styles/*.css` `package.json` `main.tsx` `App.tsx` ほか | 同じ |
| 環境 | React 19 / Vite 8 / TS 6 / Vitest 4 | React 18 / Vite 5 / TS 5 / Vitest 2 |

**Git はこれを衝突として検知しなかった**（パスが違うので別ファイル扱い）。
そのため「マージは成功するのに、中身が二重」という状態になり、片方を破棄して寄せ直す作業が発生した。

### なぜ起きたか

1. **共通基盤（骨組み）の担当者が決まっていなかった。** 機能の担当（カレンダー・プロフィール等）だけ決めていた
2. **着手の宣言がなかった。** 同時刻に別々に「まず骨組みから作る」を始めた
3. **仕様書のディレクトリ構成を片方が変更した。** `job-dashboard/` を廃してリポジトリ直下にする変更を、
   仕様書を直してから実装した（手順は正しい）が、**チームの合意を取っていなかった**
4. **未コミットのまま長時間持っていた。** 早く push していれば相手が乗る形にできた

### 今後のルール（これを守れば再発しない）

- **共通基盤は1人が先に作り、マージするまで他の人は待つ。** 対象は以下
  - ディレクトリ構成 / `package.json` / `tsconfig` / `vite.config.ts`
  - `models.py` / `db.py` / `main.py` / `conftest.py` / `seed/load.py`
  - `Shell` / `Hero` / `FeaturePanel` / `styles/*.css` / `App.tsx` / `main.tsx`
- **着手前に「これから何を作るか」を宣言する。** 特に新しいディレクトリやファイルを作るとき
- **作業を始める前に main を確認する。** 既に誰かが作っていないかを見る
  ```bash
  git fetch origin
  git ls-tree -r origin/main --name-only | grep -E "backend/|frontend/"
  ```
- **骨組み系の変更は1日以上抱えない。** 小さく早くマージする（衝突の量は経過時間に比例する）
- **仕様書の「構成」「技術スタック」を変える提案は、実装前にチームで合意する。**
  仕様書を直してから実装するのは正しいが、**共有物の変更は合意が先**
- **定期的に main を取り込む**（`git merge main`）。別パスの重複は Git が教えてくれないので、
  人が main のファイル一覧を見て気づくしかない

### 着手前チェックリスト

- [ ] `git fetch origin` して main の最新を見た
- [ ] 自分が作ろうとしているファイルが main に既に無いか確認した
- [ ] 共通基盤に手を入れるか？ → 入れるならチームに宣言した
- [ ] 仕様書の構成・スタックを変える必要があるか？ → あるなら合意を取った

### この件の決着

- **main の構成（`job-dashboard/` 配下）に寄せる。** 理由: 既に main に入っており他メンバーの前提になっている／仕様書の原文どおり／寄せる側は未コミットなので履歴が汚れない
- **`models.py` は各担当が自分のテーブルを追記する方式**（main の方針）に従う。カレンダー担当は `Event` だけ追加
- **`react-router-dom` を導入する。** 5画面あるので遷移の仕組みが必要
- **`seed/load.py` で `drop_all` を使わない。** DB を毎回作り直すと、画面から保存したプロフィールが
  seed 投入のたびに消えてしまう（仕様書§3の「毎回作り直し」より、データを壊さないことを優先）

## 2026-07-31 メール分類をドメインベースからキーワード内容ベースへ変更

**決定**：メール分類において、送信元ドメインを登録して一律分類する `DomainRule`（振り分けルール）の
仕組みを廃止し、件名の内容（キーワード）＋AIフォールバックのみで分類する方式に変更した。

**理由**：ドメインルールが件名キーワードより優先される設計だと、同じ企業（同一ドメイン）から届く
メールがすべて同じカテゴリになってしまい、「同じ送信元から来た広告と重要なメールを分けられない」
という問題があった。担当者からの指摘を受け、分類の判定軸を送信元（誰から）ではなく件名の内容
（何が書かれているか）に一本化した。

**影響範囲**：
- `docs/spec.md` §5.1.1（ルール判定）・§4.3（受信箱の右カラム）・§6（DomainRuleテーブル廃止）・
  §7（受け入れ条件）を更新済み
- バックエンド：`services/classifier.py` からドメイン判定の分岐を削除、`routers/rules.py` と関連
  エンドポイント（`GET/POST/DELETE /api/rules`）を削除。`models.py` の `DomainRule` テーブル定義
  自体は共有スキーマとして残置（未使用）
- フロントエンド：受信箱の「⚙ 振り分けルール」（登録フォーム）を、キーワード基準を表示するだけの
  読み取り専用カード「⚙ 分類ロジック」に変更

**判定に使う情報の範囲は変更していない**：件名と送信元のみを見る方針（本文はAIに渡さない）は
そのまま維持。個人情報をAPIに送る量を最小化する当初の設計意図を壊さないため。

## 2026-08-03 想定問答生成（`generate_qa`）のフォールバック設計

**決定**：`services/ai.py` の想定問答生成関数は、メール分類（`classify_email_ai`）と同じ
フォールバック方針で実装した。

- **API呼び出し失敗時は1回だけ再試行してから諦める（合計2回）**。
  理由：通信失敗・タイムアウト・レート制限は一時的な事象であることが多く、1回の再試行で
  救える可能性がある一方、無制限に再試行するとデモ中の応答が長時間止まってしまう。
  「一度だけ試して、それでもダメなら切り上げる」バランスとして2回に固定した
  （メール分類の既存実装と揃え、`services/ai.py` 内で挙動を一貫させるため）
- **`refusal`・出力異常（構造化出力が空）・2回失敗のいずれも `seed/questions.json` の
  テンプレートにフォールバックする**。理由：発表本番で `ANTHROPIC_API_KEY` が無い／API が
  不安定な状況でも、画面が固まったりエラー画面になったりせず、想定問答が必ず何かしら
  表示される状態を優先した（仕様書§5.6・§7受け入れ条件の「AIが落ちてもデモが止まらない」と同じ考え方）。
  `refusal` は `content` を読まずに即フォールバックする（生成AIが拒否した内容を無理に解釈しない）
- **DBへの保存（既存レコードの削除→入れ替え）はこの関数の責務にしていない**。
  `generate_qa` はAI呼び出しとフォールバック判断だけを行い、`(items, source)` を返す。
  DB操作は呼び出し側（`routers/qa.py`）に置くことで、この関数を純粋な単体テスト対象にした

**テスト方針**：`unittest.mock.patch` で `services.ai._get_client` を差し替え、
`client.messages.parse` の戻り値・例外・`stop_reason` をモックで制御して検証した
（`backend/tests/test_ai.py`）。**実際に Anthropic API を呼ぶテストは書いていない**。
CLAUDE.md の「テストが失敗したら期待値を実挙動に書き換えない」方針と、spec.md §3の
「AI部分のテスト方針（LLMの非決定性への対処）」に従い、AIが生成する文章の内容ではなく
「モックへの差し替え・フォールバック分岐・呼び出し回数」だけをテスト対象にしている。
これにより `ANTHROPIC_API_KEY` が無い環境でも `pytest` が決定的に通る。

## 2026-08-03 今日画面の一覧はカード内スクロールで全件表示する

**決定**：今日画面（`/`）の「今日やること」「今日返すべきメール」「今日のタイムライン」は、
件数で打ち切らず、カードの中（`.body.scroll`）をスクロールして全件たどれるようにする。
`＋ 他 N件` は使わない。

**理由**：タスク管理では**すべてのタスクが見えている方が可読性が高い**。
何件残っているかを把握してから着手したいのに、上位4件だけ見せて残りを別ページに送ると、
「今日の動きが1画面で分かる」という案03の目的にむしろ反する。

**`DESIGN_RULES.md` との関係（重要）**：

- R1「1画面完結・ページスクロール禁止」は**維持している**。
  `.page{height:100dvh}` ＋ `overflow:hidden` はそのままで、スクロールするのはカードの内側だけ。
  **一覧が伸びてもページの高さは伸びない**ので、R1 の目的（ページを縦に伸ばさない）は満たしている
- R2「一覧の常時表示は3件（最大4件）まで／あふれは `＋ 他 N件`」と
  §7「`overflow:auto` によるページ内スクロールでの高さ超過回避をしない」は、
  **ページ全体の高さ超過を防ぐための規定**と解釈し、カード内スクロールはこれに当たらないと判断した
- そのため `DESIGN_RULES.md` の本文は変更していない。`docs/spec.md` §4.1 と §7 のみ更新した

**影響範囲**：`frontend/src/pages/Today.tsx`（件数の切り出しを削除）、
`frontend/src/styles/components.css`（`.body.scroll` を追加）、`docs/spec.md` §4.1 / §7。
受信箱・想定問答など他の画面には適用していない（必要になったら同じ判断を流用する）。

## 2026-08-03 研究にあてられる時間と空き時間を分けて出す

**決定**：可処分時間 08:00〜22:00（14h）は変えず、その内訳を2つの指標に分けた。

| 指標 | 定義 |
|---|---|
| 研究にあてられる時間 | 10:00〜17:00（7h）− その枠に重なる予定 |
| 空き時間 | 14h − 研究枠 7h − 枠外の予定 − 未完了タスクの見積り合計 |

**理由**：**研究は大学院に居る間しかできない**（ペルソナの実態）。1日の空き時間をまとめて
「研究にあてられる時間」と呼ぶと、深夜の空きまで研究時間に数えてしまい実態と合わない。
時間帯を分けたうえで、ペルソナのゴール（連絡対応の手間を最小化し、浮いた時間を研究や課題に充てる）に
対応させるため、**タスクの見積りは空き時間の側から引く**ことにした。
これにより「就活タスクを片付けると空き時間が増える」が数字で見える。
研究にあてられる時間は予定だけで決まるのでチェックでは動かない。

**あわせて決めたこと**：

- タスクを差し込む空きスロットは**研究枠の外だけ**に出す（研究の時間を就活で潰さないため）。
  研究枠の空きはタイムラインに `研究 Nh` として出す
- 完了したタスクは**末尾に移動させず**、締切順のまま打ち消し線にする（どれを片付けたかが分かるため）
- 締切を過ぎているのに未完了の行は黄色文字（`--warn`）にする。
  判定の基準時刻は `services/freetime.py` の `SEED_NOW_TIME`（12:20。実運用では `datetime.now()`）
- 丸めは**半数切り上げ**。Python の `round()` は偶数丸めで 7.25h→7.0h・7.75h→8.0h と挙動が揺れ、
  発表で説明できなくなるため使わない

**影響範囲**：`docs/spec.md` §4.1 / §5.3 / §7 / 付録デモ動線を更新。
`backend/services/freetime.py`・`routers/today.py`・`routers/tasks.py`、
`frontend/src/api/eventMap.ts`（カレンダー画面の研究時間も同じ定義に統一）、
`backend/seed/tasks.json`（`ES提出` の見積りを 240分→90分。旧計算に合わせた値で、
そのままだと空き時間が 0h になりデモで動きが見えないため）。

**旧仕様との違い**：以前は「14h − 予定 − 未完了タスク見積り」を研究にあてられる時間としていた。
`docs/spec.md` §7 の「イベント4h・タスク150分で 7.5h」「チェックで研究時間が増える」は
成立しなくなったため、受け入れ条件を書き換えた（テストの期待値を実挙動に合わせたのではなく、
仕様変更として条件そのものを差し替えている）。

## 2026-08-03 AI呼び出しをAnthropicからAzure OpenAIに切り替え

**決定**：`services/ai.py`のAI呼び出しを、Anthropic API（`claude-opus-5`）からAzure OpenAI
（Responses API、`client.responses.parse()`）に切り替えた。

**理由**：担当者B（メール担当）が発行しようとしていたAnthropicのAPIキーが用意できず、代わりに
社内で用意された認証情報がAzure OpenAI用だった。当初は「Anthropicのキーを別途発行してもらう」
案と「Azure OpenAIに切り替える」案の2つを検討したが、手元にある資格情報をそのまま使える後者を
チームの合意のもとで選んだ。技術スタックの変更にあたるため、実装前にこの記録を残す。

**実装の要点（Anthropic版との違い）**：
- SDK：`anthropic` → `openai`（`AzureOpenAI`クライアント）
- 呼び出し方式：**Chat Completions API（`client.chat.completions.parse()`）ではなく
  Responses API（`client.responses.parse()`）を使う**。社内Azureリソースのエンドポイントが
  `/openai/responses`向けだったため、Chat Completions形式で呼ぶと
  `Unsupported parameter: 'response_format'`という400エラーになった（実際に発生させて確認済み）
- モデル指定：`claude-opus-5`のような固定モデル名ではなく、`.env`の`AZURE_OPENAI_DEPLOYMENT`
  （Azure側のデプロイ名）を渡す
- 構造化出力の受け取り：`res.parsed_output` → `res.output_parsed`
- refusal判定：`res.stop_reason == "refusal"` という単純なフラグが無いため、
  `res.output`内の`type="refusal"`コンテンツの有無と`res.status`（`"failed"`/`"incomplete"`）の
  両方をチェックする形に変えた
- リトライ回数（1回だけ再試行して失敗ならフォールバック）とテンプレートへの
  フォールバック方針そのものは変更していない

**検証方法**：SDKの実際のクラス定義（`inspect`でメソッドのシグネチャ・戻り値の型を確認）を見てから
実装した。想像で書いたAPIは使っていない。さらに実際のAzure OpenAI認証情報で実呼び出しを行い、
メール分類が`decided_by="ai"`で返ってくることを確認済み（`backend/tests/test_ai.py`のモックだけでなく
実機でも確認した）。

**影響範囲**：`backend/services/ai.py`・`backend/tests/test_ai.py`・`docs/spec.md`
（§2 AIの利用について／§3 技術スタック・AI呼び出しの規約／§5.1.2／§5.6／§7の受け入れ条件／
付録のデモ動線）・`.env.example`（`ANTHROPIC_API_KEY`→`AZURE_OPENAI_API_KEY`等4変数）を更新した。

**未確認の点**：このAzureリソースが「入力をモデルの学習に使わない」設定になっているかは
未確認（`docs/spec.md`にも明記した）。発表前にチームで確認する。

## 2026-08-05 アプリ全体の「今日」を固定日付から実日付に切り替え

**決定**：`services/freetime.py`の`resolve_day()` / `resolve_now()`の既定値を、固定値
（`SEED_TODAY = 2026-07-30`・`SEED_NOW_TIME = 12:20`）から実際の`date.today()` / `datetime.now()`に
切り替えた。フロントの`Calendar.tsx`の`BASE_DATE`（同じく`'2026-07-30'`固定だった）も合わせて
実日付に変更した。

**理由**：担当者Bの要望により、担当者A（今日画面・カレンダー・タスクの担当）に確認の上で実施。
`docs/spec.md`の元の設計は「実運用では`date.today()`に差し替える」ことを前提に
固定値を置いていたため、本来この切り替えは想定内の変更である。

**影響**：`seed/*.json`のダミーデータは引き続き2026-07-30前後の日付のままなので、
実際の「今日」がその範囲から離れるほど、カレンダー・タスク・今日画面の表示するイベントや
締切が0件に近づく。デモ本番でこの状態にならないよう、当日までにseedデータの日付を
実施日に合わせて調整するか、元の固定値に一時的に戻すかを、発表直前にチームで判断する必要がある。
